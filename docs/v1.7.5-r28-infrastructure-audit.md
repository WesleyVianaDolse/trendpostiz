# R28 — etapa 1: auditoria operacional somente de leitura

Preparação local em 16/11/2026. **Não houve execução na VPS.** Esta entrega não inicia H/I, não solicita sua autorização, não certifica contenção e não altera a matriz 30/31, flags, imagem, banco ou versão. A causa específica do travamento original continua desconhecida.

## Arquivo único para o operador

Script independente: [r28-infrastructure-readonly.py](../scripts/recovery/r28-infrastructure-readonly.py). Requer Linux, Python 3.8+ e Docker CLI já existentes. Não instala nada. Use o arquivo revisado no próprio host da VPS e execute manualmente:

```sh
sudo python3 -I -B r28-infrastructure-readonly.py
```

Se o arquivo estiver no checkout revisado, use seu caminho `scripts/recovery/r28-infrastructure-readonly.py`. `-I` isola a inicialização do Python e `-B` impede criação de bytecode. Não é necessário dar permissão de execução, instalar/ativar serviço ou copiar qualquer configuração de produção para o ambiente local.

A saída é NDJSON: um objeto curto por linha, somente metadados permitidos. Para análise, fornecer apenas essa saída sanitizada. Não anexar `docker inspect`, dump PM2, `.env`, logs completos, unidades/cron brutos, payloads ou históricos dos clientes. O script não cria arquivo de saída; um eventual redirecionamento é escolha manual do operador.

Opções disponíveis, sem valores sensíveis:

```sh
sudo python3 -I -B r28-infrastructure-readonly.py --app-container postiz
sudo python3 -I -B r28-infrastructure-readonly.py --no-exec
```

`--no-exec` omite o subprocesso auxiliar de leitura no container e registra lacuna Temporal. `--pm2-home <diretorio_local>` inclui um PM2_HOME não padrão que o operador já conhece. `--queue <fila_legada_revisada>` inclui até oito filas adicionais, sem buscar workflows. Diretórios/filas personalizados são referenciados por hashes na saída. Não colocar credenciais nas opções.

O diagnóstico padrão usa **um `docker exec` em container existente**, exclusivamente para executar um Node auxiliar que importa o SDK Temporal instalado em `/app/node_modules/@temporalio/client`. Não carrega NestJS, orchestrator, providers, Prisma ou código da aplicação. Não inicia worker, poll, daemon PM2 ou aplicação. As únicas RPCs são `GetSystemInfo`, `DescribeNamespace` e `DescribeTaskQueue`. Não há leitura de banco, listagem de workflows, históricos ou conteúdo. O exec gera somente o subprocesso e os registros operacionais normais do Docker; não cria container, muda configuração persistida, arquivos, ambiente salvo ou políticas de restart. Se a política local também impedir esse subprocesso, utilizar `--no-exec`; não contornar a restrição.

O subprocesso usa a configuração Temporal já herdada pelo container. Certificados e eventual API key são consumidos localmente, em memória, pelo SDK; não são transferidos ou impressos. Configuração mTLS parcial é recusada. Preloads/debug e caches de compilação/coverage são desabilitados **somente nesse subprocesso**, sem alterar o ambiente persistido. Erros, stderr e saída inesperada são descartados, com código genérico de lacuna. O host revalida o envelope antes de imprimir seus campos.

Nomes conhecidos (`postiz`, `postiz-temporal`, `orchestrator`, filas do candidato e `default`) permanecem legíveis. Outros nomes, caminhos e identidades recebem `ref:<hash>`, para correlacionar objetos sem revelar dados. O ID de imagem é distinguido do digest de registry/índice OCI. `candidate_identifier_hint=true` é somente coincidência de identificador observado, **não atestação do binário**.

`status=GAP` significa consulta ausente/falha, acesso insuficiente, formato não suportado ou limite de coleta. Código de saída 2 indica coleta parcial; 0 indica somente que as leituras previstas terminaram sem essas falhas. **Nenhum código significa aprovação de R28 ou autorização de consumo.** A seção final permanece `EVIDENCE_ONLY_NEEDS_REVIEW` e `persistent_containment_proven=false`.

## Limites que precisam permanecer explícitos

- O alvo Temporal consultado é o herdado pelo container. O script não lê `/proc/*/environ` nem arquivos dotenv. Dumps PM2 podem conter ambientes privados: são lidos e parseados somente na VPS para extrair os metadados permitidos; seus campos de ambiente/argumentos são descartados, nunca impressos ou transferidos. Overrides privados de PM2/dotenv, outros endereços/namespaces e outros daemons Docker precisam ser conferidos localmente pelo operador, sem exportar seus ambientes. Não afirmar que a consulta comprova a configuração efetiva de todo processo.
- Dependências Docker vêm de labels Compose/links/rede; não constituem o grafo completo da configuração original ou de suas condições de startup. Não executar `docker compose config` bruto para complementar a coleta: ele pode expandir segredos.
- Não se chama `pm2 jlist`, `pm2 list` ou `pm2 ping`. Daemon vivo, PIDs e configuração persistida são apresentados separadamente. Arquivo `.pid` pode estar desatualizado; PID de dump/home no container pertence ao namespace de origem. A correlação final exige os PIDs/ancestralidade observados.
- O catálogo é o conjunto exato de 32 filas do candidato local. Temporal não oferece aqui uma enumeração autoritativa de todas as filas históricas; este diagnóstico não consulta payloads para descobri-las. `unknown_queue_discovery=false` exige revisão de filas legadas/customizadas e outros namespaces antes de H.
- Pollers podem permanecer no cache de descrição após desconexão. Identidade/build reportados não provam digest nem protocolo. Zero pollers agora não exclui PM2 salvo, `restart:always`, timers, cron, outro host ou um processo capaz de reconectar depois.
- Homes PM2 customizados, outros usuários/hosts, rootless Docker, supervisores externos, launchers indiretos e configurações renderizadas em memória podem exigir investigação direcionada. O script sinaliza indirection não resolvida e não reivindica descoberta completa. Não executa scripts de startup para descobrir o que fariam.
- Symlinks internos de containers são retidos para revisão em vez de seguir inadvertidamente um destino absoluto no host. Arquivos sem acesso e truncamentos são lacunas; não são ausência comprovada de configuração.
- Limites de coleta: 384 registros normais de saída, mais aviso de truncamento e resumo; 128 containers/imagens/redes/objetos por grupo; 32 raízes de containers; 8.192 processos/entradas de unidade por varredura; 64 unidades no show; 512 arquivos de startup; arquivos de até 1 MiB, com limites menores para unidades/wrappers/PIDs. Pollers: contagem total e até três identidades por tipo; truncamento é explícito. Não aumentar limites para exportar dados brutos.
- Não mede startup nativo, tempo de inventário completo, aplicação dos lotes ou revalidação dos históricos. O tempo do diagnóstico e seus 64 DescribeTaskQueue não substituem o orçamento de admissão.

## Riscos conhecidos a partir do repositório

O Compose versionado declara `restart: always` e inicia PM2 para orchestrator, frontend e backend. O caminho histórico usa `pm2 start pnpm ... -- start`; há também script `pm2` no pacote do orchestrator. Uma imagem v1.7.4 anterior aos guards não passa a respeitá-los por existirem tabelas novas no PostgreSQL. Se voltar a executar com acesso ao Temporal e credenciais antigas, poderá consumir backlog e produzir efeitos. **São fatos do código/configuração, não prova do estado atual da VPS.**

O código local novo mantém o preflight fechado e recusa escopo PRODUCTION. O candidato é um worker separado, não substitui automaticamente backend/frontend nem torna produtores/reconciliadores antigos seguros. O observador externo entregue permanece OBSERVE_ONLY. Não será ativado nem usado para tentar curar a causa desconhecida do travamento.

## Como impedir especificamente o retorno da v1.7.4

Não basta desligar o processo atualmente visível nem confiar no `preflight` da versão nova. Antes de solicitar H, o plano nominal de contenção deverá cobrir conjuntamente:

1. Cada container/processo antigo capaz de consumir, seus pais/supervisores e qualquer backend/cron/reconciliador com esse papel. Preservar IDs e evidências para auditoria; não usar stop/kill por padrão amplo.
2. Políticas Docker e definições Compose antigas, unidades e timers, PM2 atual e dump/backup, startup/linger e cron. Impedir resurrection após restart do daemon e reboot. Não depender de apagar uma imagem: ela pode ser recriada ou baixada novamente.
3. Fronteira que recuse o consumidor antigo **mesmo quando ele não executa guard algum**. A identidade do poller ou o certificado sozinho não atesta versão. Acesso ao Temporal deve ser exclusivo dos consumidores revisados; consumidor antigo não pode obter chaves/mounts/sockets do novo artefato. A negação de egresso também deve ser avaliada para impedir efeito fora do fluxo protegido.
4. Verificação de persistência por configuração real e ensaio negativo autorizado, preferencialmente primeiro em réplica isolada. Não realizar reboot/restart/teste de reconexão em produção sem autorização própria. Não alterar o Temporal, reiniciar serviços ou revogar credenciais implicitamente nesta preparação.
5. Reversão que mantenha essa fronteira. Nunca recolocar v1.7.4 nas mesmas filas/credenciais, remover as decisões de vencimento, fazer down migration ou liberar incertos para tentar restaurar serviço.

## Validação desta entrega

Testes locais usam somente arquivos temporários e respostas sintéticas. Os testes Python verificam sanitização, proteção de symlinks, namespaces de PID, PM2 salvo, wrappers/cron/systemd, Docker remoto recusado, projeções, lacunas e rejeição de comandos mutantes. O ensaio Node executa o probe com transporte SDK simulado e allowlist de RPCs/módulos, cobrindo 32 filas/64 descrições, API key/mTLS sem vazamento, configuração parcial e erros sensíveis. Não houve acesso Docker real, rede, VPS, banco ou API social nesses testes; não são certificação operacional.

Resultado: **16/16 testes Python e 8/8 verificações SDK simuladas aprovados**; sintaxe conferida também pela gramática Python 3.8. Os testes Python executaram no Windows com Python 3.14.5: não equivalem a executar o diagnóstico no Linux da VPS. Adicionalmente, uma consulta local projetada de `docker image inspect` confirmou o candidato existente como `linux/amd64`; nenhum container foi iniciado, criado, parado ou modificado.

Arquivos de teste: `diagnostics/recovery/test-r28-infrastructure.py` e `test-r28-sdk-probe.cjs`. O [resultado local](../diagnostics/recovery/r28-infrastructure-readonly-results.json) registra totais e hashes. Todos os 1.108 arquivos da revisão anterior continuam com os mesmos hashes; guards/aplicador/flags não foram alterados. A inclusão deste novo script no checkout altera o conjunto do antigo artefato de revisão de fontes, que permanece histórico; não altera a imagem já construída, cujo contexto copiou somente os scripts de runtime/preflight. Não regenerar/admitir imagem de produção como efeito desta auditoria.
